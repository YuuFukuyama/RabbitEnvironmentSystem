# 4. SHT31詳細設計

## 4.1 接続方式

STM32とSHT31をI2Cで接続する。

```text
STM32              SHT31

SCL  ───────────── SCL
SDA  ───────────── SDA
3.3V ───────────── VIN
GND  ───────────── GND
ADR  開放（アドレス 0x44）
RST  開放
ALR  開放
```

RST は基板上のプルアップでリセットが掛からない。通信エラーの復旧に RST は使わない。ALR も使わない。

## 4.2 I2Cアドレス

SHT31のI2Cアドレスは以下を使用する。

```text
初期値：0x44
```

※使用するブレークアウト基板のADR設定を確認する。

| 項目 | 型 | 単位 |
|---|---|---|
| temperature | float | ℃ |

# 6. 危険度レベル

温度・湿度の個別危険度と、継続時間による危険度を以下の順で扱う。

```text
NORMAL < WARNING < DANGER < CRITICAL
```

個別センサー判定でCRITICALとなった場合は、継続回数を待たず総合危険度をCRITICALとする。WARNINGの継続時間による昇格条件と、複数センサーの組み合わせは次節で定義する。センサー通信やWi-Fiなどの異常状態は環境危険度とは別に管理する。

---

# 7. 温湿度複合判定

温度・湿度を個別に判定し、次の規則で総合危険度を決定する。

| 温度の個別危険度 | 湿度の個別危険度 | 総合危険度 |
|---|---|---|
| NORMAL | NORMAL | NORMAL |
| WARNING | NORMAL | WARNING |
| NORMAL | WARNING | WARNING |
| WARNING | WARNING | DANGER |
| いずれかがCRITICAL | 任意 | CRITICAL |

WARNINGが単独で継続した場合の時間による昇格は、通知制御に従う。一度上昇した総合危険度は、NORMALへ復帰するまで低下させない。NORMALへ復帰した時点で継続時間と通知段階をリセットする。

---

# 8. 異常判定の継続条件

一時的な値による誤通知を防ぐため、通知条件を危険度ごとに分ける。

| 総合危険度 | 通知条件 |
|---|---|
| WARNING | 検知回数が3回に達した時点で初回通知 |
| DANGER / CRITICAL | 検知回数の条件を待たず通知 |

## WARNING検知回数の更新

| 検知結果 | WARNING検知回数 | NORMAL連続検知回数 |
|---|---|---|
| WARNING | 1加算 | 0にリセット |
| NORMAL | 1減算（0未満にはしない）。4回連続検知時は0にする | 1加算 |
| DANGER | 1加算し、加算後に2未満なら2にする | 0にリセット |
| CRITICAL | 1加算し、加算後に3未満なら3にする | 0にリセット |
| 測定失敗 | 変更しない | 0にリセット |

NORMALを検知するたびにWARNING検知回数を1減算するが、0未満にはしない。NORMALが4回連続した時点ではWARNING検知回数を0にし、NORMAL連続検知回数も0に戻す。NORMAL以外の検知または測定失敗が発生した場合、NORMAL連続検知回数を0にリセットする。

## 10分周期の場合

WARNINGが連続して検知されると、3回目は初回検知から約20分後に成立する。

```text
0分：WARNINGを初回検知（1回目）
10分：WARNINGを検知（2回目）
20分：WARNINGを検知（3回目、通知）
```

この場合の実経過時間（約20分）は、要件定義・基本設計に記載された約30分と異なる。本書ではサンプル数を優先し、他の設計書は別途改訂する。

| 低温警告 | 10℃超18℃未満 | 19℃以上 |

# 11. 通知制御

## 11.1 通知の基本ルール

```text
異常発生通知
継続通知
正常復帰通知
生存確認通知
システム異常通知
```

環境に関するLINE通知には総合危険度（NORMAL、WARNING、DANGER、CRITICAL）を明記する。システム異常通知では環境危険度と混同しないよう、システム状態を明記する。

## 11.2 通知抑制

同一異常が継続している場合、11.3の危険度別ルールに従って通知を抑制・再通知する。

```text
WARNINGを3回連続検知 → 初回通知
 ↓
WARNING継続 → 30分後に再通知
 ↓
WARNINGを60分継続 → DANGERへ昇格して通知
 ↓
DANGERは20分ごとに再通知
 ↓
DANGERを30分継続 → CRITICALへ昇格
```

## 11.3 通知レベル

| 危険度 | 通知方式 |
|---|---|
| WARNING（注意） | 3回連続検知後に通知 |
| DANGER（危険） | 状態への遷移時に通知し、20分ごとに再通知 |
| CRITICAL（極めて危険） | 状態への遷移時に通知し、その後は測定ごとに通知 |

通知タイマーはSTM32の単調増加タイマーで計測する。時刻起点は次のとおりとする。

### WARNING（注意）

- WARNINGを初回検知した時刻から60分継続した場合、DANGERへ昇格する。
- 3回連続検知時に初回通知する。
- 初回通知時刻から30分後に再通知する。DANGERへ昇格した場合は、この再通知を行わず、DANGERの通知間隔へ移行する。

### DANGER（危険）

- DANGERへの遷移時に通知する。
- DANGER開始時刻から20分ごとに再通知する。
- DANGERが30分継続した場合、CRITICALへ昇格する。

### CRITICAL（極めて危険）

- CRITICALへの遷移時に通知する。
- CRITICALの間は10分ごとの測定ごとに通知する。

個別センサー判定がCRITICALの場合も、CRITICALへの遷移時に即時通知する。総合危険度がNORMALへ戻った場合に通知段階とタイマーをリセットする。正常復帰通知は、同一異常エピソードですでに異常通知を行っている場合に送信する。

# 14. STM32 ⇔ ESP32-C3通信

通信方式：

```text
UART
```

STM32とESP32-C3間はUARTで接続する。ESP32-C3ではATファームウェアを使用し、UART上でATコマンドと応答を送受信する。

理由：

- 構成がシンプル
- デバッグしやすい
- STM32とESP32-C3の通信に適している

## 14.1 データ形式
ATコマンドを通信制御に使用する。使用するATファームウェアとコマンドセット、UART通信速度、データ表現、行終端、応答タイムアウトは未決定とする。これらを決定後、STM32から送る測定値・状態の項目と形式を定義する。

## 14.2 STOP mode中の受信

STOP mode中は、SYSCLKから分けたAPBクロックが止まる。USARTとI2Cはこのクロックでビットを見るため、STOP中は線の変化を感知しない。USARTの受信割り込みもI2Cの割り込みも発生しない。この型番には、USARTがSTOPから復帰して受信フレームを保持する機能はない。STOP中に届いたバイトはSTM32に残らない。

STOPからの復帰に使えるのは、有効にしたEXTI割り込みだけである。いま有効なのはRTCアラームで、EXTIの17番線につながる。RX端子の立ち下がりも、EXTI割り込みを有効にすれば同じ種類の復帰要因になる。無効のEXTIは、端子がLになってもCPUを起こさない。

クロックを起動するのは、有効な割り込み要求がCPUに届いたときである。ハードウェアがSTOPを解除し、HSI（8 MHz）を起動する。割り込みハンドラがフラグを消す処理がクロックを入れているのではない。`main`は先頭からやり直さず、`WFI`の次から続く。72 MHzへ戻すのは、その次の`SystemClock_Config()`である。

RTCは32.768 kHzのLSEでカウントを続ける。アラーム時刻になるとEXTI 17番が立ち、同じ順でHSIが起動する。

RX端子のEXTIで起こす場合、ESP32-C3は通常のUART送信だけを行う。EXTI向けの命令は出さない。アイドルはHなので、送り始めたスタートビットのH→LをSTM32のEXTIが保持する。ピンの割り当ては`firmware/usart.md`に従う。

EXTIの立ち下がりは、STOPに入る直前にだけ有効にする。復帰して端子をUSARTのRXへ戻すときに無効に戻す。有効なまま通常受信すると、1バイトごとのスタートビットで同じ割り込みが入る。

ハンドラの処理は常に同じとする。EXTIのペンディングレジスタへ1を書き、立ち下がりの印を消す。メッセージの内容は読まない。STOP中かどうかの分岐はハンドラに書かない。消さずに残すと、同じ割り込みが直後にもう一度入る。STOPに入る直前に残っていると、スタートビットが無くてもすぐに起きる。

復帰後に測定へ戻るかUARTを読むかは、`WFI`から戻ったメイン側で、RTCアラームかRXのEXTIかを見て分ける。

起こした先頭バイトは、USARTが止まっているあいだに過ぎる。ESP32-C3は、その1バイトを送り切ったあと、線をアイドル（H）のまま10 ms空け、そのあと本データを送る。STM32からのready通知は行わない。この10 msは、クロック復帰の直後にUSARTを受信できる状態へ戻す前提である。10 msのあいだにセンサー測定などを挟む場合は、その時間を待ちに足す。`HSE_STARTUP_TIMEOUT`の100 msは、HSEが起動しなかったときの失敗判定であり、毎回の待ち時間ではない。

RX端子のEXTIが担うのはSTOPの解除だけである。起こし用GPIOをRXとは別の端子にし、RXはUSARTのままにする構成の方が、ピンの切り替えがなく先頭バイトを落とさない。どちらで起こすかは未決定とする。

LINEからの要求は、ESP32-C3が先に受けてからSTM32を起こす向きになる。ESP32-C3がスリープ中でWebhookの受信先も無いあいだは、STM32の解除方法だけではLINEメッセージは届かない。Webhook経路は17章のとおり未決定とする。

## 14.3 早期復帰とRTCアラーム

RTCアラームはカウンタの絶対時刻である。RXのEXTIなどで測定時刻より早く起きても、アラーム時刻は動かない。測定周期を維持するときはアラームを解除せず、UART処理のあと、同じアラームを有効なままSTOPへ戻る。このときに`RTC_ArmAlarm()`を再度呼ぶと、今から測り直した時刻に書き換わり、測定間隔が伸びる。

早期復帰を新しい測定周期の始まりにするときだけ、アラームを新しい時刻でセットし直す。「いまの状態」の操作で早く起きた場合は、新しい測定周期の始まりにしない。測定とアラームの扱いは17.1節に従う。

UART処理中に予定時刻を過ぎた場合、現行の`RTC_Alarm_IRQHandler`はアラームフラグとEXTIのペンディングを消すだけで、メインへは通知しない。そのあと元のアラームを待ってSTOPに入ると、二度とRTCでは起きない。STOPへ戻る前にカウンタが予定時刻を過ぎていないか確認し、過ぎていれば測定してから次のアラームをセットする。

# 16. Wi-Fi切断時の動作

Wi-Fiが切断されても、STM32による温湿度測定は継続する。STM32は最新の測定値と現在の環境危険度をRAMに保持する。

```text
Wi-Fi切断
 ↓
ESP32-C3が再接続
 ↓
成功
 ↓
最新状態を送信
```

Wi-Fi復旧後は、蓄積した全測定履歴ではなく、最新の測定値と復旧時点で有効な異常状態を送信する。電源断をまたぐデータ保持は行わない。

# 17. LINE Messaging API通信

ESP32-C3からHTTPSでLINE Messaging APIへ接続する。

```text
ESP32-C3
 ↓
HTTPS
 ↓
LINE Messaging API
 ↓
LINE
```

中継サーバーは初期版では使用しない。

本章の通信は、STM32/ESP32-C3からLINEへの送信と、17.1節の利用者操作の受信を定義する。利用者操作を受けるには、LINEからのWebhookイベントを受信する経路が別途必要となる。Webhook受信先および中継サーバーを使用しない構成は未決定とする。

STOP mode中のSTM32はUARTを受信できない。測定周期のあいだにLINEからのコマンドをSTM32へ届けるには、ESP32-C3が起きていて、14.2節に従ってSTM32をSTOPから戻してからUARTで渡す。両方止まっているあいだに届いたメッセージをSTM32が拾う経路は、現仕様には無い。

LINEメッセージで日時設定コマンドを受信した場合、入力値を検証してSTM32 RTCへ設定し、設定結果と設定後の日時をLINEで返信する。コマンド形式は次のとおりとする。

```text
日時設定 YYYY-MM-DD HH:MM:SS
```

日時はJSTで指定する。コマンドの受信・認証経路は、17.1節の利用者操作と共通のWebhook経路を使用する。

## 17.1 利用者向けボタン

利用者の操作は、常時表示するリッチメニューと、メッセージに添えるクイックリプライで受ける。リッチメニューは半分の高さ（2500×843）とし、横3列で次の3つを置く。

| ボタン | 動作 |
|---|---|
| いまの状態 | その場で測定し、結果を返す |
| 定期通知 | 生存確認通知の現在のON/OFFを返し、クイックリプライで切り替える |
| その他 | 案内とともに、平均・詳細・日時設定のクイックリプライを出す |

生存確認通知の利用者向けの名称は「定期通知」とする。受信の前提は本章冒頭と同じとし、ESP32-C3が要求を受けてからSTM32を起こす。

### いまの状態

「いまの状態」を受けた場合、保存済みの直近測定値は返さず、SHT31を測定し直す。測定結果でLCDを更新する。5章から7章の閾値で、この1回の測定値を判定する。継続回数や時間による昇格は適用しない。LINEへ返す内容は次のとおりとする。

- 測定した温度、湿度
- この測定値から判定した危険度
- 継続中の異常がある場合は、保持している総合危険度と継続時間
- システム状態
- 測定日時（JST）
- 生存確認通知のON/OFF

```text
【いまの状態】
今回の危険度：NORMAL（正常）

温度：22.5℃
湿度：52.3%

システム状態：NORMAL
測定日時：2026-10-05 11:48:00
定期通知：オン
```

継続中の異常がある場合は、今回の危険度に加えて総合危険度と継続時間を書く。

```text
【いまの状態】
今回の危険度：WARNING（注意）
総合危険度：DANGER（危険）
継続時間：60分

温度：27.5℃
湿度：65.2%

システム状態：NORMAL
測定日時：2026-10-05 11:48:00
定期通知：オン
```

センサー取得に失敗した場合は、21.5節と同じく最後に正常取得した温度・湿度と経過時間を返し、危険度は変えない。起動後に正常取得が一度もない場合は、温度・湿度を返さず未取得とする。RTC日時が未設定の場合は、測定日時を返さず未設定とする。経過時間は単調増加タイマーで数えるため、RTC日時が未設定でも返す。RTC日時が未設定で、過去の正常値がある場合は次のとおりとする。

```text
【いまの状態】
センサーエラー 12分
危険度は変えていません。

温度：22.5℃
湿度：52.3%

システム状態：SENSOR_ERROR
日時：未設定
定期通知：オフ
```

予定の測定時刻を過ぎていない手動測定では、異常通知と生存確認通知を送らない。WARNINGの検知回数、再通知の間隔、通知段階も進めない。保持している総合危険度も変えない。RTCアラームは14.3節に従い、予定の測定時刻を維持する。この測定は10分周期のログに加えない。

処理中に予定時刻を過ぎていた場合だけ、この測定をその回の定期測定として扱う。定期測定と同じ判定、ログ、通知を行い、次のアラームをセットする。いずれの場合も、「いまの状態」への返信は行う。

# 21. LCD詳細設計

LCDは16桁×2行とし、10分ごとの測定・状態検知ごとに表示を更新する。総合危険度がNORMALのときは危険度名を出さず、上段に温度、下段に湿度を表示する。WARNING・DANGER・CRITICALでは上段に危険度を表示する。WARNING以上では、WARNING以上を最初に検知した時点からの継続時間を整数分で上段に続け、下段に温度と湿度を並べる。危険度が上昇しても経過時間はリセットせず、NORMALへ復帰した時点でリセットする。測定失敗時はセンサーエラー表示を優先する。温度は「T:」、湿度は「H:」に続けて小数1桁で書く。WARNING以上またはセンサーエラーのときはアイコン S56 を点灯し、NORMAL のときは消灯する。温湿度取得がダミーのときはアイコン S37 を点灯する。S56 とは独立で、ダミーのあいだは警告中も消さない。本番取得では S37 は消灯のままにする。

# 22. LCD通信

ST7032i LCDとSTM32をI2Cで接続する。

```text
STM32 SCL ──┬── SHT31 SCL
            └── ST7032i SCL
STM32 SDA ──┬── SHT31 SDA
            └── ST7032i SDA
```

アドレスは ST7032i が `0x3E`、SHT31 が `0x44` で重ならない。バス速度、転送の区切り、エラー時の復旧手順は `firmware/i2c.md` に従う。

起動時の LCD 初期化が、バス復旧のあと再試行しても失敗したときは `Error_Handler` に入る。周期中の表示更新が失敗しても測定は止めない。失敗したフレームは途中まで書いたままにし、次に成功した周期で 2 行を書き直す。失敗のたびに Clear Display はしない。

# 25. 消費電力設計

消費電力の大きい処理として特にWi-Fi通信を考慮する。STM32は測定・通知処理の完了後、次回測定時刻までSTOP modeに入り、32.768 kHzのLSE水晶をクロック源とするSTM32 RTCのアラームで10分周期に復帰する。RTCアラーム発生から測定処理再開までの約1秒の遅延は許容する。STOP modeによる消費電力低減は、バックアップ電源を使用する場合の停電時稼働時間の延長にも活用する。

VBAT端子およびRTCバックアップ電源は使用しない。VDDが失われるとRTC日時は保持されず、再起動後はLINEの日時設定コマンドを受け付けるまでRTC日時を無効とする。STOP mode中はVDDが維持されるためRTCは動作を継続する。

```text
STM32 STOP mode（次回測定まで待機）
 ↓ STM32 RTCアラームで10分周期に復帰
温湿度測定・異常判定・LCD更新
 ↓
ESP32-C3起動、Wi-Fi接続
 ↓
測定値・必要な通知を送信
 ↓
ESP32-C3はスリープへ移行
 ↓
STM32は次回測定までSTOP mode
```

STOP modeは停電を直接検知する機能ではなく、バックアップ電源がない場合は電源喪失により動作を継続できない。バックアップ電源の容量は別途決定する。30分ごとの生存確認は10分周期測定の3回ごとに同時送信し、独立したWi-Fi接続は行わない。Wi-Fi接続中に送信対象がない場合の扱いを含む、ESP32-C3の具体的なスリープ方式は未決定とする。

STOP mode中のUART受信、復帰に使える割り込み、RX端子のEXTIで起こすときの手順は14.2節に従う。測定時刻より早い復帰とRTCアラームの関係は14.3節に従う。現在の測定周期の復帰要因はRTCアラームのみである。

# 28. エラー処理

止めるのは、起動時の LCD 初期化がバス復旧のあと再試行しても失敗したときだけである。このときは `Error_Handler` に入る。周期中の I2C エラーは、バスを戻してからそのデバイスの失敗として測定を続ける。

1 周期の順は、センサ取得、判定、LCD 更新、通知である。タイムアウトでバスが掴まれたまま次へ進むと、同じ周期の LCD も、次の周期のセンサも失敗する。復旧は ST7032i と SHT31 の両方の転送の下で、失敗を返す前に 1 回だけ行う。手順は `firmware/i2c.md` に従う。

| 起きたこと | すること |
| --- | --- |
| アドレス NACK | その転送は失敗とする。I2C ペリフェラルはそのまま |
| CRC 不一致 | センサ異常とする。バスも SHT31 も触らない |
| タイムアウト、バスビジー、バスエラー | STOP を出す。BUSY が残れば I2C を初期化し直す。SDA が L のままなら SCL を 9 クロック出してから I2C に戻す。そのあと失敗として返す |
| LCD 初期化の失敗 | 上の復旧のあと初期化をもう一度だけ試す。それでも失敗なら `Error_Handler` |
| 周期中の SHT31 失敗 | 測定値を正常値として扱わない |
| 周期中の LCD 更新失敗 | 表示の戻りは捨て、測定と通知は続ける |

## SHT31エラー

```text
SHT31通信失敗
 ↓
命令、15 ms、6 バイト読み、CRC の一式を 1 回だけ取り直す
 ↓
成功 → 通常処理
失敗 → SENSOR_ERROR。危険度は変えない。通知を 1 件出す
```

2 回目も失敗した表示は、21.5 節のとおりである。過去に正常値があれば最後の温湿度と経過分、無ければ `NO DATA` を出す。LED のトグルと次周期の待ちはそのまま続ける。NACK のあと、待ちだけ足して同じ読み出しを繰り返さない。

ソフトリセット `0x30A2` は、この 1 周期の取り直しには使わない。バスが空いたまま NACK または CRC 不一致が周期をまたいで続くときに、次の測定の前へ 1 回送り、次の命令まで 1.5 ms 空ける。汎用コールリセット（アドレス `0x00`、2 バイト目 `0x06`）は送らない。

## リセット端子

通信エラーの復旧に、リセットピンは繋がない。

SHT31 の RST は開放のままとする。バスが空いているときの復帰は `0x30A2` で行い、バスが止まっているときは SCL を 9 クロック出してインタフェースを戻す。RST を GPIO で叩くのは、バス復旧のあとでもソフトリセットに NACK が続く場合に限る。1 回の NACK や CRC 不一致では RST を使わない。SDA を掴んでいるのが ST7032i のときは、SHT31 の RST ではバスは空かない。

ST7032i の XRESET は、電源条件を外して内部リセットが動かなかったときのための端子である。通信のたびに使うと、40 ms とフォロワ後 200 ms の初期化からやり直しになり、表示も消える。

STM32 の nRESET はマイコン自身のリセットである。スレーブの RST はここへつながない。

# 30. ログ

## 30.1 保持範囲と記録内容

ログは10分ごとに1件の測定記録として保持する。各記録には次の情報を含める。

- 温度
- 湿度
- 現在状態
- 記録日時（JST）
- SHT31通信結果、ESP32通信結果、Wi-Fi接続状態、LINE送信結果
- エラーコードまたはエラー内容
- 再接続回数

通信結果、エラーコードまたはエラー内容、再接続回数は、その測定周期内の結果として記録する。周期内に複数回再試行した場合は最終結果と再接続回数を記録し、個々の再試行ごとの履歴は保持しない。

取得対象は要求時点から遡る直近48時間のログに限定する。期間は「要求時点の48時間前より後、要求時点まで」とし、暦日による当日・前日の区分は行わない。10分周期の測定記録は最大288件を保持し、48時間より古い記録は削除する。

初期版ではログをRAM上に保持し、電源断またはリセットをまたぐ保存は行わない。このため、再起動後に再起動前のログを取得できる保証はない。STM32のSRAM使用量を抑えるため、記録は固定長の数値・状態コードで保持する。1件16バイトを目標とした場合、測定記録領域は約4.5 KiBとなる。実際の空きSRAMはリンク後のメモリ使用量で確認する。

## 30.2 LINEログ取得

ログ情報の出力先はLINEのみとし、ファイル出力やLCDへのログ一覧表示は行わない。利用者は17.1節のクイックリプライから次の要求を送る。

| 要求 | 出力内容 |
|---|---|
| 詳細 | 要求時点から遡る直近48時間の全ログ記録 |
| 平均 | 要求時点から遡る直近48時間の平均情報 |

詳細出力には、対象期間内の各記録の日時、温度、湿度、環境危険度、システム状態、通信結果、エラー情報および再接続回数を含める。対象期間内に記録がない場合は、その旨をLINEで返す。

最大288件の詳細ログはLINEのメッセージ制限に合わせて複数メッセージに分割する。各メッセージに対象期間と分割番号を付け、全記録を省略せず順番に送信する。

## 30.3 LINE平均出力

平均出力は直近48時間内の正常な測定記録を対象とし、温度・湿度の算術平均を出力する。測定失敗記録は平均計算から除外し、測定失敗回数として別に表示する。時間は平均値ではなく、集計対象の開始・終了日時および記録数として出力する。

環境異常回数は、正常な測定記録のうち総合危険度がWARNING、DANGERまたはCRITICALであった測定回数とする。出力項目は対象期間、集計時間範囲、正常測定件数、平均温度、平均湿度、環境異常回数および測定失敗回数とする。
