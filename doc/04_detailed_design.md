# 3. STM32詳細設計

## 3.1 STM32の役割

STM32をシステムのメイン制御部とする。

主な処理：

- SHT31から温湿度を取得
- 温湿度の異常判定
- 異常状態の管理
- LCDへの表示
- ESP32-C3への測定結果の送信
- ESP32-C3から受け取ったLINE操作の適用
- 照会への返答
- 測定周期の管理
- 通知要求の生成
- システム状態の管理

LINEのユーザーID、許可リスト、利用者ごとの定期通知のON/OFFは持たない。誰かONかどうかは、起動時に1回だけ受け取り、リセットまで保持する。

# 4. SHT31詳細設計

## 4.1 接続方式

STM32とSHT31をI2Cで接続する。

```text
STM32              SHT31

SCL  ───────────── SCL
SDA  ───────────── SDA
3.3V ───────────── VIN
GND  ───────────── GND
ADR  開放（アドレス 0x44）
RST  開放
ALR  開放
```

RST は基板上のプルアップでリセットが掛からない。通信エラーの復旧に RST は使わない。ALR も使わない。

## 4.2 I2Cアドレス

SHT31のI2Cアドレスは以下を使用する。

```text
初期値：0x44
```

※使用するブレークアウト基板のADR設定を確認する。

基本測定周期：


測定処理：

```text

 ↓
SHT31へ測定要求
 ↓

 ↓
データチェック
 ↓
異常判定
 ↓
LCD更新
 ↓
中継サーバーへ送信
 ↓
待機
```

## 4.4 センサーデータ

| 項目 | 型 | 単位 |
|---|---|---|
| temperature | float | ℃ |
| humidity | float | %RH |
| elapsed_time_ms | uint32_t | STM32起動後の経過時間 (ms) |
| timestamp | datetime | 中継が付ける日本時間 |
| sensor_status | enum | センサー状態 |

測定周期や通知間隔はSTM32の単調増加タイマーで計測する。LINEへ出す履歴の日付と時間は、中継が測定を受けた時刻を日本時間にして付ける。STM32のRTC暦日時は、この履歴に使わない。10分周期のアラームは、暦日時がなくても動く。電源投入またはリセットのあと、最初に中継と通信できた操作取得の応答で、日本時間と、誰か定期通知がONかを1回受け取る。日本時間はRTCの暦日時へ書く。通知モードはリセットまで保持する。STOPからの復帰では取り直さない。取得に失敗しても測定は続ける。モードが未取得のあいだは生存確認を出さない。

# 6. 危険度レベル

温度・湿度の個別危険度と、継続時間による危険度を以下の順で扱う。

```text
NORMAL < WARNING < DANGER < CRITICAL
```

個別センサー判定でCRITICALとなった場合は、継続回数を待たず総合危険度をCRITICALとする。WARNINGの継続時間による昇格条件と、複数センサーの組み合わせは次節で定義する。センサー通信やWi-Fiなどの異常状態は環境危険度とは別に管理する。

---

# 7. 温湿度複合判定

温度・湿度を個別に判定し、次の規則で総合危険度を決定する。

| 温度の個別危険度 | 湿度の個別危険度 | 総合危険度 |
|---|---|---|
| NORMAL | NORMAL | NORMAL |
| WARNING | NORMAL | WARNING |
| NORMAL | WARNING | WARNING |
| WARNING | WARNING | DANGER |
| いずれかがCRITICAL | 任意 | CRITICAL |

WARNINGが単独で継続した場合の時間による昇格は、通知制御に従う。一度上昇した総合危険度は、NORMALへ復帰するまで低下させない。NORMALへ復帰した時点で継続時間と通知段階をリセットする。

---

# 8. 異常判定の継続条件

一時的な値による誤通知を防ぐため、通知条件を危険度ごとに分ける。

| 総合危険度 | 通知条件 |
|---|---|
| WARNING | 検知回数が3回に達した時点で初回通知 |
| DANGER / CRITICAL | 検知回数の条件を待たず通知 |

## WARNING検知回数の更新

| 検知結果 | WARNING検知回数 | NORMAL連続検知回数 |
|---|---|---|
| WARNING | 1加算 | 0にリセット |
| NORMAL | 1減算（0未満にはしない）。4回連続検知時は0にする | 1加算 |
| DANGER | 1加算し、加算後に2未満なら2にする | 0にリセット |
| CRITICAL | 1加算し、加算後に3未満なら3にする | 0にリセット |
| 測定失敗 | 変更しない | 0にリセット |

NORMALを検知するたびにWARNING検知回数を1減算するが、0未満にはしない。NORMALが4回連続した時点ではWARNING検知回数を0にし、NORMAL連続検知回数も0に戻す。NORMAL以外の検知または測定失敗が発生した場合、NORMAL連続検知回数を0にリセットする。

## 10分周期の場合

WARNINGが連続して検知されると、3回目は初回検知から約20分後に成立する。

```text
0分：WARNINGを初回検知（1回目）
10分：WARNINGを検知（2回目）
20分：WARNINGを検知（3回目、通知）
```

この場合の実経過時間（約20分）は、要件定義・基本設計に記載された約30分と異なる。本書ではサンプル数を優先し、他の設計書は別途改訂する。

# 9. ヒステリシス

| 状態 | 開始条件 | 解除条件 |
|---|---|---|
| 低温警告 | 10℃超18℃未満 | 19℃以上 |
| 高温警告 | 26℃以上28℃未満 | 正常（NORMAL）。18℃以上26℃未満 |
| 乾燥警告 | 15%超40%未満 | 41%RH以上 |
| 高湿度警告 | 60%以上70%未満 | 59%RH未満 |

WARNING状態へ遷移した後は解除条件を適用する。低温異常（10℃以下）、高温異常（28℃以上）、湿度異常（15%以下または70%以上）にはヒステリシスを適用しない。

# 10. 状態管理

STM32では環境危険度とシステム稼働状態を分けて保持する。

環境危険度：
```text
NORMAL
WARNING
DANGER
CRITICAL
```

システム稼働状態：
```text
NORMAL
SENSOR_ERROR
WIFI_ERROR
SYSTEM_ERROR
```

環境危険度の通知は11章に従う。システム稼働状態の異常は環境危険度を上書きせず、システム異常通知の対象として管理する。

# 11. 通知制御

## 11.1 通知の基本ルール

```text
異常発生通知
継続通知
正常復帰通知
生存確認通知
システム異常通知
```

環境に関するLINE通知には総合危険度（NORMAL、WARNING、DANGER、CRITICAL）を明記する。システム異常通知では環境危険度と混同しないよう、システム状態を明記する。

## 11.2 通知抑制

同一異常が継続している場合、11.3の危険度別ルールに従って通知を抑制・再通知する。

```text
WARNINGを3回連続検知 → 初回通知
 ↓
WARNING継続 → 30分後に再通知
 ↓
WARNINGを60分継続 → DANGERへ昇格して通知
 ↓
DANGERは20分ごとに再通知
 ↓
DANGERを30分継続 → CRITICALへ昇格
```

## 11.3 通知レベル

| 危険度 | 通知方式 |
|---|---|
| WARNING（注意） | 3回連続検知後に通知 |
| DANGER（危険） | 状態への遷移時に通知し、20分ごとに再通知 |
| CRITICAL（極めて危険） | 状態への遷移時に通知し、その後は測定ごとに通知 |

通知タイマーはSTM32の単調増加タイマーで計測する。時刻起点は次のとおりとする。

### WARNING（注意）

- WARNINGを初回検知した時刻から60分継続した場合、DANGERへ昇格する。
- 3回連続検知時に初回通知する。
- 初回通知時刻から30分後に再通知する。DANGERへ昇格した場合は、この再通知を行わず、DANGERの通知間隔へ移行する。

### DANGER（危険）

- DANGERへの遷移時に通知する。
- DANGER開始時刻から20分ごとに再通知する。
- DANGERが30分継続した場合、CRITICALへ昇格する。

### CRITICAL（極めて危険）

- CRITICALへの遷移時に通知する。
- CRITICALの間は10分ごとの測定ごとに通知する。

個別センサー判定がCRITICALの場合も、CRITICALへの遷移時に即時通知する。総合危険度がNORMALへ戻った場合に通知段階とタイマーをリセットする。正常復帰通知は、同一異常エピソードで DANGER または CRITICAL の通知を送り切っている場合に送信する。WARNING だけでは送らない。

# 12. 正常復帰通知

DANGER または CRITICAL の通知を送り切ったあと、正常状態へ戻った場合、LINEへ復帰通知を送信する。WARNING だけでは送らない。

```text
【正常復帰】
環境危険度：正常

温度：23.1℃
湿度：54.2%

温湿度が正常範囲に戻りました。
```

# 14. STM32 ⇔ ESP32-C3通信

通信方式：

```text
UART
```

STM32とESP32-C3間はUARTで接続する。ESP32-C3ではATファームウェアを使用し、UART上でATコマンドと応答を送受信する。

理由：

- 構成がシンプル
- デバッグしやすい
- STM32とESP32-C3の通信に適している

## 14.1 データ形式
ATコマンドを通信制御に使用する。UART通信速度、UART上のデータ表現、行終端、応答タイムアウトは未決定とする。中継へ送る測定の項目は17.2節で決めた。ヘッダは `AT+HTTPCHEAD`、測定の本文は `AT+HTTPCPOST` に置く。

## 14.2 STOP mode中の受信

STOP mode中は、SYSCLKから分けたAPBクロックが止まる。USARTとI2Cはこのクロックでビットを見るため、STOP中は線の変化を感知しない。USARTの受信割り込みもI2Cの割り込みも発生しない。この型番には、USARTがSTOPから復帰して受信フレームを保持する機能はない。STOP中に届いたバイトはSTM32に残らない。

STOPからの復帰に使えるのは、有効にしたEXTI割り込みだけである。いま有効なのはRTCアラームで、EXTIの17番線につながる。RX端子の立ち下がりも、EXTI割り込みを有効にすれば同じ種類の復帰要因になる。無効のEXTIは、端子がLになってもCPUを起こさない。

クロックを起動するのは、有効な割り込み要求がCPUに届いたときである。ハードウェアがSTOPを解除し、HSI（8 MHz）を起動する。割り込みハンドラがフラグを消す処理がクロックを入れているのではない。`main`は先頭からやり直さず、`WFI`の次から続く。72 MHzへ戻すのは、その次の`SystemClock_Config()`である。

RTCは32.768 kHzのLSEでカウントを続ける。アラーム時刻になるとEXTI 17番が立ち、同じ順でHSIが起動する。

LINE操作は、測定周期の途中には渡さない。STM32がRTCアラームで起きているあいだに、ESP32-C3が中継サーバーから取得した操作をUARTでSTM32へ渡す。

## 14.3 早期復帰とRTCアラーム

RTCアラームはカウンタの絶対時刻である。測定周期を維持するときはアラームを解除せず、処理のあと、同じアラームを有効なままSTOPへ戻る。このときに`RTC_ArmAlarm()`を再度呼ぶと、今から測り直した時刻に書き換わり、測定間隔が伸びる。

LINE操作で測定時刻より早く起こすことはしない。

UART処理中に予定時刻を過ぎた場合、現行の`RTC_Alarm_IRQHandler`はアラームフラグとEXTIのペンディングを消すだけで、メインへは通知しない。そのあと元のアラームを待ってSTOPに入ると、二度とRTCでは起きない。STOPへ戻る前にカウンタが予定時刻を過ぎていないか確認し、過ぎていれば測定してから次のアラームをセットする。

# 16. Wi-Fi切断時の動作

Wi-Fiが切断されても、STM32による温湿度測定は継続する。STM32は最新の測定値と現在の環境危険度をRAMに保持する。

```text
Wi-Fi切断
 ↓
ESP32-C3が再接続
 ↓
成功
 ↓
中継サーバーへ最新状態を送信
```

Wi-Fi復旧後は、蓄積した全測定履歴ではなく、最新の測定値と復旧時点で有効な異常状態を中継サーバーへ送信する。電源断をまたぐデータ保持は行わない。

# 17. LINE Messaging API通信

通知と利用者操作は中継サーバーを通す。ESP32-C3はLINE Messaging APIを呼ばない。チャネルアクセストークンとチャネルシークレットは中継サーバーだけが持つ。

```text
ESP32-C3
 ↓
HTTPS
 ↓
中継サーバー
 ↓
LINE Messaging API
 ↓
LINE
```

中継サーバーはLINEのWebhookを受け、署名を検証し、許可したLINEユーザーIDの操作だけを保管する。中継が持つ情報は [../relay/doc/setup.md](../relay/doc/setup.md) の「サーバーが持つ情報」に書く。

同じ種類の未処理操作は最新1件にまとめる。「いまの状態」、平均、詳細は未処理操作にしない。中継の履歴から返す。定期通知のON/OFFは未処理操作にせず、中継サーバーが利用者ごとに持つ。STM32は利用者の情報を持たない。LINEからの日時設定は行わない。電源投入またはリセットのあと、時刻と通知モードをまだ受け取っていないあいだは、操作取得の応答に中継の現在時刻（日本時間）と、誰か定期通知がONかを載せる。別のリクエストにはしない。STM32は時刻をRTCの暦日時へ書き、通知モードをリセットまで保持する。両方書けたあとの周期には載せない。取得に失敗しても測定は止めない。モードが未取得のあいだは生存確認を出さない。

STM32はRTCアラームで10分ごとに起きる。10分周期のアラームに暦日時は不要である。その接続でESP32-C3が未処理の操作を取得し、UARTでSTM32へ渡す。ESP32-C3は中継サーバーとのHTTPSと、操作と測定結果の受け渡しに限る。周期の途中に、LINE操作のためにSTOPを解除しない。STOP中はUARTを受信できない。この事実は14.2節に従う。

1周期の順は、操作の取得、起動後まだならその応答の時刻をRTCへ書き通知モードを保持する、STM32への通知、設定の適用、測定、判定、LCD更新、中継サーバーへの送信とする。誰か定期通知がONかは、この起動時の応答でだけ受け取る。

中継サーバーへ届かないときは、次の周期に最新状態を送る。過去の定期測定の通知はまとめて送らない。通信できなかった測定は、履歴に穴のまま残す。

中継サーバーの設置場所は [05_relay_server.md](05_relay_server.md) で決定した。許可するLINEユーザーIDの登録方法と、中継が持つ情報は [../relay/doc/setup.md](../relay/doc/setup.md) で決定した。本体と中継のHTTPのパス、本文、本体認証は17.2節で決定した。

## 17.1 利用者向けボタン

利用者の操作は、常時表示するリッチメニューと、メッセージに添えるクイックリプライで受ける。リッチメニューは半分の高さ（2500×843）とし、横3列で次の3つを置く。「いまの状態」、平均、詳細は中継が履歴から返す。定期通知のON/OFFは中継がすぐ返す。

| ボタン | 動作 |
|---|---|
| いまの状態 | 履歴の最新1件を返す |
| 定期通知 | 中継が、その利用者のON/OFFをすぐ返し、クイックリプライで切り替える。切り替えた返信で本体のリセットを案内する |
| その他 | 案内とともに、平均・詳細のクイックリプライを出す |

生存確認通知の利用者向けの名称は「定期通知」とする。

### いまの状態

「いまの状態」を受けた場合、中継が履歴の最新1件を返す。本体の次の測定は待たない。履歴がなければ未取得とする。日付と時間は、その記録をサーバーが受けた日本時間である。LINEへ返す内容は次のとおりとする。

- 温度、湿度
- 温度の状態、湿度の状態
- 危険度
- 日付と時間
- 生存確認通知のON/OFF（中継が持つ設定。本体が今使っているモードは、リセット前にはずれることがある）

```text
【いまの状態】
危険度：正常

温度：22.5℃
湿度：52.3%

温度の状態：正常
湿度の状態：正常
日時：2026-10-05 11:48:00
定期通知：オン
```

履歴がなければ、温度・湿度を返さず未取得とする。

### 定期通知

「定期通知」を受けた場合、中継サーバーがその利用者のONかOFFかをすぐLINEで返す。続けてクイックリプライで「オン」と「オフ」を出し、選ばれた方を設定する。設定後の状態をLINEで返し、本体をリセットすると反映される旨を伝える。24時間でOFFにはしない。オンもオフも、利用者の設定として中継に残す。本体が生存確認を出すかと、送り先は、次のリセットの起動時に読み直すまで変えない。

```text
定期通知：オン
本体をリセットすると反映されます。
```

```text
定期通知をオフにしました。
本体をリセットすると反映されます。
```

LINEへ送る生存確認通知の見出しは、18章のとおり「【定期通知】」とする。

### その他

「その他」を受けた場合、次の案内とともにクイックリプライを出す。

```text
操作を選んでください。
```

| ボタン | 動作 |
|---|---|
| 平均 | 30.3節の平均を返す |
| 詳細 | 30.2節の詳細ログを返す |

「詳細」はログ取得であり、環境異常の通知ではない。平均と詳細の出力内容は30章に従う。

## 17.2 本体と中継のHTTP

本体から中継へのHTTPSは、操作の取得と測定の送信である。どちらも `Authorization: Bearer` に、Worker の Secret `DEVICE_TOKEN` の値を付ける。値そのものは31章のとおり文書に書かない。欠落や不一致は401とし、履歴にもLINEにも反映しない。応答に302は返さない。

ESP32-C3のATは1コマンド256バイトまでである。本文はコマンド行に埋め込まない。ヘッダは `AT+HTTPCHEAD`、測定の本文は `AT+HTTPCPOST` に置く。

通知するかはSTM32が決める。利用者IDと、利用者ごとのON/OFFの一覧は本体へ渡さない。

### 操作取得

`GET /v1/ops`

未処理操作を返す。電源投入またはリセットのあと、時刻と通知モードをまだ返していない応答には、次を載せる。両方を返せたあとの周期には載せない。STOPからの復帰では取り直さない。

| 項目 | 内容 |
|---|---|
| `time` | 日本時間の ISO 8601。例は `2026-10-11T21:00:00+09:00`。STM32はRTCの暦日時へ書く。履歴の日時には使わない |
| `notifyMode` | 誰か定期通知がONなら1、そうでなければ0。1を返した時点でONのユーザーIDを、中継が次の起動まで定期通知の送り先として覚える |

取得に失敗しても測定は続ける。`notifyMode` が未取得のあいだは、生存確認の `periodic` を0のままにする。

### 測定送信

`POST /v1/measurements`

中継は届いた測定を毎回、履歴へ足す。`notify` が0でも残す。`at` は中継が受けた時刻の日本時間である。本体の時刻は履歴に使わない。`notify` と `periodic` は履歴に残さない。履歴の項目と件数は30.1節である。

```json
{"humidity":52.3,"temperature":22.5,"humidityState":"HUM_BEST","temperatureState":"TEMP_BEST","danger":"NORMAL","notify":0,"periodic":0}
```

| 項目 | 内容 |
|---|---|
| `humidity` | 湿度 |
| `temperature` | 温度 |
| `humidityState` | 湿度の状態。`HUM_BEST`、`HUM_DRY` など |
| `temperatureState` | 温度の状態。`TEMP_BEST`、`TEMP_CRIT` など |
| `danger` | 全体の危険度。`NORMAL`、`WARNING`、`DANGER`、`CRITICAL` |
| `notify` | 0は異常としてのLINE通知を出さない。1は11章の異常、12章の復帰、システム異常。中継は許可済みユーザーと管理者の全員へ、18章の同じ文面を送る。未許可の友だちには送らない |
| `periodic` | 起動時の `notifyMode` が1で、60分ごとの生存確認の周期のときだけ1。それ以外は0。このとき `notify` は0。中継は覚えた送り先へ「【定期通知】」を送る |

同じ周期に `notify` と `periodic` が両方1のときは、異常の文面だけを全員へ送る。定期通知は重ねない。

成功は200。届かないときは、次の周期に最新状態を送る。過去の定期測定はまとめて送らない。通信できなかった測定は、履歴に穴のまま残す。

# 19. 生存確認機能

生存確認は、起動時に `notifyMode` が1だったとき、10分ごとの測定周期と同期し、60分ごとの測定時に `periodic` を1にして送る。このとき `notify` は0である。リセットまでこの判定は変えない。送り先は、中継が `notifyMode` を返したときにONだった利用者である。起動後にLINEでオンまたはオフにしても、次のリセットまで送り先は変えない。該当利用者へ送るかは中継が決める。

ON/OFFは中継サーバーが利用者ごとに持つ。24時間でOFFにはしない。共有の開始時刻は持たない。オンにした利用者のIDを足し、オフにした利用者のIDを外す。利用者のIDやON/OFFの一覧はSTM32へ渡さない。渡すのは、起動時の操作取得の `notifyMode` だけである。誰もONでないとき、また未取得のあいだは、`periodic` を0のままにする。

```text
起動時に誰かON
 ↓
60分経過
 ↓
生存確認通知（その起動時にONだった利用者）
 ↓
60分経過
 ↓
生存確認通知
```

利用者向けの名称は「定期通知」とし、切り替えは17.1節のボタンで行う。中継がすぐ返し、本体のリセットを案内する。

# 20. 停電への対応

初期版では停電を直接検知しない。

代替として、起動時に定期通知がONだったあいだの60分ごとの生存確認通知を利用する。

通知が届かなくなった場合は、

```text
停電
または
Wi-Fi障害
または
インターネット障害
または
本体停止
```

などの可能性がある。

したがって、システム上は「通知が届かない＝停電」と断定しない。

この決定は要件定義に残る停電検知要求および優先順位と一致していない。初期版では本節の仕様を適用し、要件定義は別途改訂課題とする。

# 21. LCD詳細設計

LCDは16桁×2行とし、10分ごとの測定・状態検知ごとに表示を更新する。総合危険度がNORMALのときは危険度名を出さず、上段に温度、下段に湿度を表示する。WARNING・DANGER・CRITICALでは上段に危険度を表示する。WARNING以上では、WARNING以上を最初に検知した時点からの継続時間を整数分で上段に続け、下段に温度と湿度を並べる。危険度が上昇しても経過時間はリセットせず、NORMALへ復帰した時点でリセットする。測定失敗時はセンサーエラー表示を優先する。温度は「T:」、湿度は「H:」に続けて小数1桁で書く。WARNING以上またはセンサーエラーのときはアイコン S56 を点灯し、NORMAL のときは消灯する。温湿度取得がダミーのときはアイコン S37 を点灯する。S56 とは独立で、ダミーのあいだは警告中も消さない。本番取得では S37 は消灯のままにする。Wi-Fi に接続できたときはアイコン S1 を点灯し、接続できなかったときだけ消灯する。測定後に AP から外れても消灯しない。S56 および S37 とは独立である。

# 22. LCD通信


# 25. 消費電力設計

消費電力の大きい処理として特にWi-Fi通信を考慮する。STM32は測定・通知処理の完了後、次回測定時刻までSTOP modeに入り、32.768 kHzのLSE水晶をクロック源とするSTM32 RTCのアラームで10分周期に復帰する。RTCアラーム発生から測定処理再開までの約1秒の遅延は許容する。STOP modeによる消費電力低減は、バックアップ電源を使用する場合の停電時稼働時間の延長にも活用する。

VBAT端子およびRTCバックアップ電源は使用しない。VDDが失われるとRTCの暦日時は保持されない。次の起動後、最初に中継と通信できたときに取り直す。取得できなければ暦は無効のまま、測定は続ける。STOP mode中はVDDが維持されるため、10分周期のアラームは動作を継続し、時刻の取り直しはしない。

```text
STM32 STOP mode（次回測定まで待機）
 ↓ STM32 RTCアラームで10分周期に復帰
ESP32-C3起動、Wi-Fi接続、中継サーバーから操作を取得
 ↓
操作をSTM32へ通知し、設定を適用
 ↓
温湿度測定・異常判定・LCD更新
 ↓
測定値・必要な通知・操作への返答を中継サーバーへ送信
 ↓
AT+CWRECONNCFG=0,0 のあと AT+CWQAP を送り、ESP32-C3 は AP から外れる
 ↓
STM32は次回測定までSTOP mode
```

STOP modeは停電を直接検知する機能ではなく、バックアップ電源がない場合は電源喪失により動作を継続できない。バックアップ電源の容量は別途決定する。60分ごとの生存確認は、起動時に誰かONだったときだけ、10分周期測定の6回ごとに同時送信する。独立したWi-Fi接続は行わない。送信のあと STM32 は `AT+CWRECONNCFG=0,0` と `AT+CWQAP` をこの順で送る。ESP32-C3 は次の測定まで AP に戻らない。切断に失敗しても測定は続ける。アンテナは接続できなかったときだけ消す。測定後の切断では消さない。`AT+CWJAP` で再接続間隔を省略すると v3.3.0.0 では 1 秒で戻り直すため、切る前に間隔 0 を書く。チップのスリープ方式は未決定とする。

STOP mode中はUARTを受信できない。この事実と、LINE操作を測定周期の中で渡す手順は14.2節に従う。LINE操作で測定時刻より早く起こすことはしない。測定周期の復帰要因はRTCアラームのみである。

# 27. 60分生存確認処理

生存確認は10分周期の測定と同じタイマーを使い、起動時に誰か定期通知がONだったとき、起動後60分ごとに測定と同時に `periodic` を1にする。このとき `notify` は0である。リセットまでこの判定は変えない。誰もONでないとき、未取得のとき、および生存確認の周期以外でも、10分周期の測定と異常通知は継続する。その場合の `periodic` は0である。

```text
起動時：測定
10分：測定
20分：測定
30分：測定
40分：測定
50分：測定
60分：測定＋生存確認（起動時に誰かONだった場合）
```

# 28. エラー処理

止めるのは、起動時の LCD 初期化がバス復旧のあと再試行しても失敗したときだけである。このときは `Error_Handler` に入る。周期中の I2C エラーは、バスを戻してからそのデバイスの失敗として測定を続ける。

1 周期の順は、センサ取得、判定、LCD 更新、通知である。タイムアウトでバスが掴まれたまま次へ進むと、同じ周期の LCD も、次の周期のセンサも失敗する。復旧は ST7032i と SHT31 の両方の転送の下で、失敗を返す前に 1 回だけ行う。手順は `firmware/i2c.md` に従う。

| 起きたこと | すること |
| --- | --- |
| アドレス NACK | その転送は失敗とする。I2C ペリフェラルはそのまま |
| CRC 不一致 | センサ異常とする。バスも SHT31 も触らない |
| タイムアウト、バスビジー、バスエラー | STOP を出す。BUSY が残れば I2C を初期化し直す。SDA が L のままなら SCL を 9 クロック出してから I2C に戻す。そのあと失敗として返す |
| LCD 初期化の失敗 | 上の復旧のあと初期化をもう一度だけ試す。それでも失敗なら `Error_Handler` |
| 周期中の SHT31 失敗 | 測定値を正常値として扱わない |
| 周期中の LCD 更新失敗 | 表示の戻りは捨て、測定と通知は続ける |

## SHT31エラー

```text
SHT31通信失敗
 ↓
命令、15 ms、6 バイト読み、CRC の一式を 1 回だけ取り直す
 ↓
成功 → 通常処理
失敗 → SENSOR_ERROR。危険度は変えない。通知を 1 件出す
```

2 回目も失敗した表示は、21.5 節のとおりである。過去に正常値があれば最後の温湿度と経過分、無ければ `NO DATA` を出す。LED のトグルと次周期の待ちはそのまま続ける。NACK のあと、待ちだけ足して同じ読み出しを繰り返さない。

ソフトリセット `0x30A2` は、この 1 周期の取り直しには使わない。バスが空いたまま NACK または CRC 不一致が周期をまたいで続くときに、次の測定の前へ 1 回送り、次の命令まで 1.5 ms 空ける。汎用コールリセット（アドレス `0x00`、2 バイト目 `0x06`）は送らない。

## リセット端子

通信エラーの復旧に、リセットピンは繋がない。

SHT31 の RST は開放のままとする。バスが空いているときの復帰は `0x30A2` で行い、バスが止まっているときは SCL を 9 クロック出してインタフェースを戻す。RST を GPIO で叩くのは、バス復旧のあとでもソフトリセットに NACK が続く場合に限る。1 回の NACK や CRC 不一致では RST を使わない。SDA を掴んでいるのが ST7032i のときは、SHT31 の RST ではバスは空かない。

ST7032i の XRESET は、電源条件を外して内部リセットが動かなかったときのための端子である。通信のたびに使うと、40 ms とフォロワ後 200 ms の初期化からやり直しになり、表示も消える。

STM32 の nRESET はマイコン自身のリセットである。スレーブの RST はここへつながない。

# 30. ログ

## 30.1 保持範囲と記録内容

LINEへ出す測定履歴の正本は、中継の履歴である。届いた測定は毎回残す。`notify` が0でも残す。通信できなかった期間は欠測のままである。日付と時間は、中継が受けた時刻を日本時間にしたものである。平均と詳細の対象は直近24時間である。履歴は1008件（10分周期で7日）までとし、超えた分は古い測定から捨てる。1つの値は25MiB未満に保ち、`LineUsers` への許可の追加が失敗しない空きを残す。

1件に次を持つ。`notify` と `periodic` は残さない。個別危険度の項目は持たない。

- 日時（`at`）
- 温度（`temperature`）
- 湿度（`humidity`）
- 温度の状態（`temperatureState`）
- 湿度の状態（`humidityState`）
- 全体の危険度（`danger`）

```json
{"at":"2026-10-11T21:00:00+09:00","temperature":22.5,"humidity":52.3,"temperatureState":"TEMP_BEST","humidityState":"HUM_BEST","danger":"NORMAL"}
```

STM32のRAMに同じ履歴を溜めてLINEへ返すことはしない。

## 30.2 LINEログ取得

ログ情報の出力先はLINEのみとし、ファイル出力やLCDへのログ一覧表示は行わない。利用者は17.1節のクイックリプライから次の要求を送る。

| 要求 | 出力内容 |
|---|---|
| 詳細 | 直近24時間に届いた記録 |
| 平均 | 30.3節の平均 |

詳細は、直近24時間に届いた記録を、吹き出し5つまでを1回の送信に載せる。1人あたり1通である。各記録の日付と時間、温度、湿度、温度の状態、湿度の状態、危険度を含める。記録がない場合は、その旨をLINEで返す。

## 30.3 LINE平均出力

平均は、届いている記録の直近24時間を対象とする。欠測は埋めない。件数は届いた件数を出す。温度・湿度の算術平均を出力する。時間は平均値ではなく、届いた記録の開始・終了日時および記録数として出力する。

出力項目は対象期間、集計時間範囲、記録数、平均温度、平均湿度とする。
